# Generate Express Service Repo

Create a working service, not just a directory outline. Read [references/service-contract.md](references/service-contract.md) for the route adapter, schema-package compatibility, configuration, and verification details before generating files.

## Inputs and Boundaries

Collect the absolute target directory, service/package name, companion schema package name, database choice (including `none`), and publication/deployment platform (including `undecided`). Ask for missing choices; do not infer an organization, private registry, deployment credentials, database endpoint, or identity system. Ask for the local schema-package path when it is not published, or for the registry and installation access when it is private. Inspect the package's actual exports and `ApiInfo` shape before coding against it. If inaccessible, stop before claiming a working integration; do not substitute a mock schema package as the final dependency.

Confirm the target is absent or empty before writing. Respect any existing repository instructions, Git changes, and permission boundaries. Never overwrite another project. No deployment automation until the platform, registry, CI secrets, target address, and runner are confirmed. A named platform alone is not enough.

## Repository Contract

- Node >=22, pnpm, TypeScript, Express, Zod. Use current stable dependency releases resolved from their package registries during generation, pin a compatible pnpm version in `packageManager`, commit the lockfile, and verify the actual installed versions. Account for major-version compatibility (notably Express typings, Zod, Vitest, TypeScript, SWC, ESLint, and the schema package); do not guess numeric latest versions. Use public ESLint configuration unless installation of a private one is confirmed; document the difference.
- Set `main` to `build/index.js`, `type` to `commonjs`, and `engines.node` to `>=22`. TypeScript uses `module` and `moduleResolution` `NodeNext`, `target` `ES2020`, `rootDir` `src`, `outDir` `build`, `tsBuildInfoFile` `build/.tsbuildinfo`, plus `strict`, `noImplicitAny`, `noUncheckedIndexedAccess`, `esModuleInterop`, `declaration`, `sourceMap`, and `inlineSources`. Set `incremental` if required for `tsBuildInfoFile`. Production build excludes `*.test.ts` and `tests/`; provide `tsconfig.test.json` covering tests. Ensure `typecheck` and `typecheck:test` really work with `--noEmit`.
- `src/index.ts` loads environment variables before configuration and sets up any runtime aliases before importing aliased modules, then starts the HTTP server. Prefer relative imports throughout to eliminate cross-tool alias drift. If aliases are used, align TypeScript, SWC, Vitest, and Node runtime resolution and test both builds.
- `src/services/` assembles the Express app independently of `listen()`. `src/routes/` registers routes with minimal logic; `src/middlewares/` contains validation, error handling, response, and logging middleware; `src/lib/` owns business logic; `src/consts/` owns configuration/constants; `src/utils/` is business-neutral; `src/types/` is service-specific. `tests/` holds test setup/shared helpers. Create `src/queries/` only for an enabled database and `src/thirdParty/` only for an actual integration. Do not manufacture empty directories or placeholder modules.
- Depend on `express`, `zod`, `compression`, `cors`, `dotenv`, `module-alias`, `morgan`, `pino`, `pino-http`, and the named schema package. Add `typescript`, `@types/node`, `@types/express`, `@types/compression`, `@types/cors`, `@types/morgan`, `ts-node`, `@swc/core`, `@swc/cli`, `tsc-watch`, `nodemon`, `concurrently`, `vitest`, `@vitest/coverage-v8`, `supertest`, `@types/supertest`, `eslint`, `prettier`, `husky`, and `lint-staged` as dev dependencies. Add necessary public tooling such as `typescript-eslint` when required by the chosen ESLint setup; don't add unused runtime integrations.
- Provide runnable `build` (clean `build/`, then `tsc`), `build:swc` (compile `src/` to `build/`, omit `*.test.ts`), `build:swc:watch`, `typecheck`, `typecheck:test`, `start` (dotenv/config, source maps), `start:watch` (nodemon on `build/`), `dev` (watch compilation and restart), `lint`, `lint:fix`, `test`, `test:watch`, `test:coverage`, and `prepare` (install Husky hooks). Honor the intent of `husky install`, but verify the syntax supported by the resolved stable Husky version; document a necessary `prepare: husky` substitution. Make the hook actually invoke `lint-staged`.
- Supply `.env.example` with at least `HTTP_PORT`, `NODE_ENV`, and `LOG_LEVEL`; never commit `.env` or real secrets. Centralize typed environment parsing and fail startup on missing configuration for enabled features only. Include `/health`; disable `x-powered-by`; order middleware as JSON body, CORS, compression, request logging, business routes, 404, and one error handler. Production CORS must require explicit allowed origins rather than silently allowing all. Pino logs must redact credentials/tokens and avoid logging raw request bodies or authorization headers. Tests must not open real database or third-party connections by default.
- `.gitignore`: `node_modules/`, `build/`, `coverage/`, `*.tsbuildinfo`, `.env` (and local env variants except `.env.example`), log files, and local caches. Dockerfile uses Node 22, the pinned pnpm version and frozen lockfile, a build stage and non-root runtime stage. Exclude `.env`, credentials, Git metadata, caches, and local builds with `.dockerignore`. Provide CI for frozen install, lint, both typechecks, build, and unit tests, without deployment jobs or fabricated secret names.

## Conditional Integrations

Only configure requested integrations. SQL Server: `mssql`, pooled connections, parameterized queries, separate test database configuration and opt-in API integration test command; default `test` must never reset a non-test database. Sentry: `@sentry/node` enabled by `SENTRY_DSN`; no DSN must not break local HTTP. Datadog: `dd-trace` initialized before instrumented imports, no configuration must not block startup. Redis: `ioredis` with isolated connect/shutdown. AWS: only service-specific SDK v3 modules, with no invented bucket, region, or Lambda identifiers. Add `INSTANCE_MODE`/multiple entrypoints only for explicit multi-instance requirements, and never expose a local-only Combined mode in production. If a requested integration lacks essential configuration, leave it disabled or ask for that configuration; document exactly what remains.

## Finish

Document environment variables, development, tests, both builds, schema package installation/update (including formal registry installation when developing through a relative `file:` dependency), and deployment prerequisites in README. Run `pnpm install`, `pnpm lint`, `pnpm typecheck`, `pnpm typecheck:test`, `pnpm build`, and `pnpm test`. Start the built server and send HTTP requests to `/health` and the anonymous example API (valid and invalid inputs); shut it down. Independently run `pnpm build:swc`, repeat the runtime HTTP checks against its output, and ensure production builds contain no test files. Run the relevant Docker/CI checks when feasible. Report actual results, any failed or unrun checks, and unresolved external configuration. If a task-local commit is required, stage only the task's files and commit once after verification.
