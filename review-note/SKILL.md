# Review Note —— 多角色笔记知识缺口评审

把一份笔记从"记录了什么"推进到"还缺什么、哪里不扎实、该补什么"，供用户补齐、复习或用于实战。

## 工作流

### 1. 确认输入与目标
- 读取笔记：本地附件、粘贴文本，或经 notion/lark 等工具读取链接；读不到就先解决读取，不用印象代替。
- 确认主题与受众（自用复习 / 面试 / 教学 / 工作落地），受众决定深度和缺口的取舍。
- **界定笔记关注点（scope）与定位**：判断笔记是**专题型**（只聚焦某子主题，如"Redis 数据类型""Web 性能优化"）还是**体系型**（覆盖领域整体知识框架），据此确定评审边界：
  - 专题型笔记：完整性（L1）缺口只在**笔记声明的主题内部**子模块里挑；**主题之外 / 外延模块（例如给"Redis 数据类型"报缺"持久化 / 高可用 / 网络模型"）一律不评审、不列入报告**，避免拿整体知识体系去苛求一份专题笔记。
  - 体系型笔记：按领域完整框架评审，L1 缺口照常报。
  - 边界以笔记标题、目录结构、开场白声明的范围为准；拿不准时在"评审配置"里写明所采用的边界与依据。
- 选角色：优先用用户指定的角色；未指定则按笔记主题自动推断 **2~4 个**最相关角色（不要全上，避免冗余噪音）。角色画像见 `references/roles.md`。

### 2. 建立主题-结构地图（先别挑错）
梳理笔记已覆盖的主题模块，并为每个模块标注深浅档位：`提到 / 了解 / 会用 / 踩过坑`，同时标注该模块**在 / 超出笔记关注点**（超范围模块不进评审基线，直接排除在评审之外）。这张地图是后续所有评审的基线。

### 3. 四层递进评审（核心）

| 层 | 审什么 | 关注信号 |
|---|---|---|
| L1 完整性 | 主题框架是否成体系，有没有整块缺失的模块 | 缺独立主题、缺前置/进阶章节、模块之间没串起来 |
| L2 深度 | 知识点是"知道"还是"会用/踩过坑" | 只给定义不给用法、缺反例、缺适用边界、缺代码/公式推导 |
| L3 场景 | 真实场景里的边界、异常、性能、安全、反例是否覆盖 | 缺具体 case、缺"如果…怎么办"、缺极端/低配环境 |
| L4 时效正确 | 有没有过时、错误、有争议的表述 | 版本过时、已被推翻、与主流共识矛盾、含糊其辞 |

**每完成一层，切换一个新角色**，用该角色最关心的"坑"把当前层重新扫一遍（见 `roles.md`），把它发现的新缺口并入清单。缺口的证据是"笔记里没有但该场景下会被问到/会出错"，不是主观喜恶。

### 4. 收敛输出
按 `references/output.md` 模板输出。逐条缺口给全四要素：**缺口 → 为什么缺(影响/严重度) → 补什么 → 怎么补(来源或参考方向)**。不要只报缺，必须给出可执行的补全方向；来源无法确认的标"待核实"，不编造。
**只评审关注点内的缺口**：报告只列笔记定位内"该覆盖却缺失/不扎实"的项（定级 P0~P2）；关注点之外的内容不评、不列。专题型笔记的硬伤只出在关注点内，不得因缺外延模块而被打低分。

## 阅读指南
- **角色画像库** `references/roles.md`：需要某个角色视角时读取，内含该角色的关注点、典型坑、常问问题，以及自动推断角色的匹配规则。
- **输出模板** `references/output.md`：生成缺口报告时读取，含严重度分级（P0~P3）与报告结构。
